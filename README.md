# cod4-decomp

A GPL-3.0-only Rust reimplementation of the Call of Duty 4: Modern Warfare (1.7) multiplayer engine. It runs on macOS, Linux, and Windows, and includes a headless server. It contains no game content: you supply your own copy of the game.

Planning and decisions: [wayfinder map](https://github.com/jeiang/cod4-decomp/issues/1). Terms: [CONTEXT.md](CONTEXT.md). Decisions with lasting effect: [docs/adr](docs/adr).

## Build

```sh
nix develop -c cargo build --workspace
nix develop -c cargo test --workspace
```

Without Nix, install rustup; `rust-toolchain.toml` selects the toolchain.

## Original install

The engine reads a CoD4 1.7 install directly: `main/*.iwd`, `zone/<language>/*.ff`, and `localization.txt`. `cod4e`, `cod4e-server` and the harness find it the same way (`crates/install`): `--install <dir>` (the harness: `--cod4`), `COD4_PATH`, the folder remembered from an earlier prompt, the Windows registry and Steam libraries, then `./COD4`, which is gitignored. `cod4e` and the harness ask for the folder in a dialog when none is found and remember the answer (always in the platform's default config dir, `--config-dir` or not); `cod4e-server` never asks and prints where it looked. Never commit or upload anything from the install. Tests that need the install skip when it is missing.

## Logging

Every binary logs through `tracing` (crate `logging`): events go to stderr, to a log file per run (the client writes `<config dir>/logs/client-*.log` for a player's session, the newest 10 are kept; `COD4E_LOG_DIR` names another folder), and to the browser console in the web client. `warn` and `error` events from this workspace also reach the in-game console. The filter is `COD4E_LOG` or `RUST_LOG` (`EnvFilter` syntax; default `info` for our crates, `warn` for the rest); at run time the `developer` cvar (1 is `debug`, 2 is `trace`) and the `log_filter` cvar change it, in the client and in the dedicated server. Levels: `error` loses a feature or the session, `warn` is unexpected or missing state with a fallback, `info` is lifecycle, `debug` and `trace` are per-frame detail. Repeating warnings go through `logging::dedup!` (the 1st, 2nd, 4th... hit of a key with a `seen` count). Passwords, `rcon` arguments and CD keys are masked in every sink.

## Harness

`cod4e-harness` runs the staged suite under a watchdog (each stage in a child process; crashes, hangs and panics are caught) and writes `cod4e-run-<date>.zip` (at most 100 MB, user and host names scrubbed) with `manifest.json`, `summary.json`, logs, CSVs, a Perfetto-readable `trace.json` and minidumps. A run too big for that gives up files until it fits: videos first, then screenshots, then traces and CSVs, the largest file of each kind first so the most evidence stays; the smallest screenshot of each stage goes last of all, so a stage keeps a frame for `just review` as long as the cap allows. `DROPPED.txt` in the zip lists what was left out.

Every process of a stage writes its log to `<stage>/logs/` in the bundle. A stage that passes but logged a `warn` or `error` that is not in the reviewed allow-list (`crates/harness/src/logcheck.rs`, one reason per entry) is failed, with the first events in its reason; allowed events are counted in the stage's notes. `selftest-warn` proves the gate.

```sh
nix develop -c just harness run --out bundles   # default suite
nix develop -c just harness stages              # list stages
nix develop -c just harness diff a.zip b.zip    # compare two bundles
```

A running client can be driven from outside through its dev control channel (`--control <port>`, off unless asked;
see `docs/control-channel.md`), which injects the player's own input, reads the state document (menu, entities,
scoreboard, sounds, ...), waits on it and captures the presented frame. The `control-channel` stage runs that
acceptance.

Stages that need engine commands read console scripts (`scenarios/*.cfg`, or `--script file`); a command the console does not have fails the stage. A stage that reports `Skipped` (a missing display, GPU, install or build) is not a pass: it fails the run unless `--allow-skip <stage>` names it, and `summary.json` lists the skips apart from the stages that ran (`skipped`, `allowed_skips`, `unexpected_skips`); the exit status is 0 only when every stage ran and passed. Every client run writes a `render` record (`material_failures`: materials with no techset, no usable technique or a pipeline that failed to build, by name and reason; `image_failures`: images that did not load) into `client.json` and `ui-script.json`, and the stages that judge a match or a scripted run (`client-match`, `client-dedicated`, `client-hud`, `client-session` and the stages sharing its verdict) fail on any material failure and on any image that did not load, so a draw the renderer skipped or a placeholder it drew is no longer invisible. No material failures are allowed: cross-zone references (`,gfx_smk_white_atlas`) resolve while loading, so the smoke, fire, mist and glass sprites of a map's effects must draw without an exception (#453). The counters those stages read from the client's report are required: a counter the report lacks fails the stage instead of reading as zero, and `client-ui` requires every one of the fourteen menus the tour opens. Double-clicking the program runs the suite with the zip next to it. The CI `windows` job uploads that portable folder and smoke-tests it with no install. Repository tools are `just` recipes (`nix develop -c just --list`). `just remote <ref> -- <run options>` runs the suite on the Linux test host (`COD4E_LINUX_HOST`, default `artemis.jeiang.vpn`) and copies `bundles/` back. On that host `just slot <n> <ref> <stages>` runs stages in slot 1, 2 or 3 (up to three at once, each with its own headless 1920x1080 display, loopback-only network namespace and target dir), `just slot-exec <n> <ref> <command>` runs a command in a slot with the release binaries on PATH (its `out/` is copied back), `just serial <ref> [stages]` runs timing-gated stages on the host's real display with the host to itself, and `just host-status` shows which slots are busy.

Host lock waits are bounded at 30 minutes. A contended lock prints its kernel holders (`lslocks`, PID/command/path), then fails clearly on timeout. `.serial-pending` records the serial owner's PID; waiters remove a marker with a dead or missing owner and say why. Serial owners queue separately, and marker reads/writes/removal share a short lock, so an owner's cleanup cannot erase the next owner's marker. Builds still share the stage lock and timing runs still take it exclusively after building.

The exported HUD includes `sprint_facts` (weapon, weapon duration scale, `ps.perks`, `player_sprintTime`, `perk_sprintMultiplier`) next to the current sprint budget and `sprint_spawn` with the same inputs captured at the most recent spawn. Session-verdict stages check the stock `BG_GetMaxSprintTime` formula (4 seconds × weapon scale, doubled only by Extreme Conditioning, capped at 16383 ms); `client-custom-class` checks the spawn record too. A grenade `throw` step counts only missile entities owned by the local player, never another player's grenade.

`just review <bundle.zip> [--reference <bundle.zip>] [--out review.md]` (`scripts/footage-review.py`) reviews a bundle's screenshots and every second of its videos with two llama-server vision models: an EmbeddingGemma 2 server with its vision projector (`COD4E_EMBED_URL`) names each frame's scene, skips near-identical video frames and, with `--reference`, scores each frame against the frame of the same name in that bundle; a Qwen3.5 server with its projector (`COD4E_REVIEW_URL`) lists the defects it sees in each frame. The recipe points both at the Linux test host. Its findings are leads to check by eye (it also reports defects that are not there), not a gate. Videos need `ffmpeg`, which the dev shell provides.

Stage 3 (`client-flythrough`) needs a GPU and a display: it runs the `cod4e` client (`$COD4E_CLIENT`, else next to the harness) on mp_crash once per display mode (native borderless, windowed 1080p and 720p, plus an exclusive run at another native-size refresh when the monitor has one), 12 s each (`COD4E_FLYTHROUGH_SECS`), and records one short video (a few MB), a screenshot and per-frame timings per mode. It also runs mp_crash uncapped at native size (`--present immediate` and `mailbox`) and two more stock maps (mp_bog, mp_crash_snow), so the bundle shows sun shadows, fog and the film/glow post effects on three maps. `frames.csv` carries GPU pass time from timestamp queries where the device has them (`gpu_ms`, a few frames behind the render call, matched by frame number). The video is recorded at 30 fps on a background encoder thread that drops the slots it cannot keep up with; each sample carries its own duration, so the file stays in sync. The loss follows the frame size and the cores the run has: 0.6-1.7% at a 2536x1416 window and at 1280x720, 34.9-37.8% at 5120x1440, all with the host to itself, and up to 56% at 1920x1080 beside two other runs. The stage records the lost share per mode as a metric and fails only a recording that kept under 8 fps, too few frames to review; the native-resolution shortfall is #442. Without the client, an install or a display it is skipped.

## Headless server

```sh
COD4_PATH=/path/to/install nix develop -c just server +set g_gametype war +exec server.cfg +map mp_crash
```

`cod4e-server` boots like the original's dedicated server: command-line `set`s, `default_mp.cfg`, the dedicated zone set, then `+exec` and `+map`. It runs the stock gametype scripts at 30 Hz (`sv_fps`) on one thread. Console commands include `bots N` (server-side test clients that pick a team and class and play: they roam a navigation mesh generated from the map's collision data, shoot enemies they see, and inject usercmds directly, with no netchan; they join at once but wait until five seconds of level time, on every level start including a restart, before picking a team, as the stock scripts add their test clients after `wait 5`; this keeps them from spawning before the spawn logic's first sweep of the level's spawn points), `status` and `expect <stat> <min>`. Harness stage 2 (`headless-bots`, plus `headless-bots-sd` for Search and Destroy; every server stage fails over 512 MiB peak RSS) plays an 18-bot team deathmatch round on mp_crash to its time limit and the map rotation, and records `ticks.csv` (per-tick total and gsc/bot/client/game columns), RSS, map-load and navigation-generation time and match counters; `headless-bots-32` is the 32-player budget run. Stage `script-pool` plays 32 Search and Destroy rounds and a two-map team deathmatch rotation with bots and fails if the script variable pool (the original's 0xFFFE-value limit) does not return to the same level every round.

### Perks

Perks are the stock game's: the engine reads the bits the scripts set with `setPerk`/`unsetPerk`/`clearPerks` (`bg_perkNames` order, `playerState_t.perks`) for Sleight of Hand (`perk_weapReloadMultiplier`), Double Tap (`perk_weapRateMultiplier`), Extreme Conditioning (`perk_sprintMultiplier`), Steady Aim (`perk_weapSpreadMultiplier`), Iron Lungs (`perk_extraBreath`), Deep Impact (`perk_bulletPenetrationMultiplier`), Dead Silence (the `q` sound families), UAV Jammer (off the radar), Eavesdrop (`perk_parabolic*`), Martyrdom (`perk_grenadeDeath` dropped by `DeathGrenadeDrop`) and Last Stand (`lastStand` and its half-second grace in `G_Damage`, `PM_LASTSTAND` movement). The rest are the stock scripts' (`_class.gsc`): Juggernaut, Stopping Power and Sonic Boom in `cac_modified_damage`, Bandolier's `giveMaxAmmo`, Frag x3 and Special Grenades x3 counts, Bomb Squad, Overkill. `suicide()` and the console `kill` go straight to `player_die` (`PlayerCmd_Suicide`, `Cmd_Kill_f`), so the stock Last Stand gives the pistol, the health held down by its overlay thread and a ten second bleed-out, and a grenade kill is no Last Stand (`mayDoLastStand`). The `net-perks` stage asserts each of these effects on a headless server with two UDP clients whose uploaded profiles carry custom classes.

### Use triggers

`+activate` works as in the original (`src/activate.rs`): each frame the server picks the player's use trigger (`trigger_use` by the view and range, `trigger_use_touch` by standing in it, a trigger switched off for the player's team or claimed by another player does not count) and puts its cursor hint (`cursorHint`, `cursorHintString`, `cursorHintEntIndex`) in the player state; a fresh press on a hinted trigger sends it `trigger` with the player once `g_useholdspawndelay` and `g_useholdtime` allow, and a held button is not a fresh press until it is let go. The client draws the hint (owner-draw 72, `cg_cursorHints`). Search and Destroy and Sabotage plant and defuse through this: bots walk to a zone, pickup or defuse trigger that is on for their team and hold the button there (a free bomb pickup first; a carrier or a defender sent to a just-planted bomb does not stop for far-off enemies; they stand still, not sprinting, so the server takes the press). Harness stages `headless-sd-objective` and `headless-sab-objective` (8 and 16 bots, the server runs unpaced with `until plants 1 <seconds>`), `net-objective` (two real UDP clients; one plants holding +activate at the zone's hint, the other defuses; the stage places them with `devtele`) and `client-objective` (the real client plants; needs a display).

Dropped weapons and live grenades (`src/items.rs`, `sim::weapon::pickup`): `dropitem` (and the stock `dropWeaponForDeath`) leaves an item entity holding the player's magazine and the reserve their other weapons could not carry; it falls with the `g_drop*Speed*` velocities, at most `g_maxDroppedWeapons` stay (the one farthest from every player is freed), and the dropper cannot take it back for a second. Clients are sent it as an `ITEM` entity and draw the weapon's world model. Walking over one feeds a weapon the player owns (or shares ammunition with) up to its limit and plays `ammoPickup`/`pickup` sounds; +activate on a hinted one takes the weapon with its ammunition (swapping out the primary in hand when both slots are full). A live frag at rest within `player_throwbackInnerRadius` shows the throw-back hint; the grenade key takes it with the fuse left (`player_throwbackOuterRadius`, `bg_maxGrenadeIndicatorSpeed`). A player who dies cooking a grenade drops it with the fuse left, and Martyrdom (`perk_grenadeDeath`) drops another. `ItemWeaponSetAmmo` sets what an item holds. Not built: `dropitem`'s second argument (the weapon tag the item leaves from), the pickup HUD icon (`CG_ItemPickup`), and map `weapon_*` entities settling onto the floor.

Mountable turrets (`src/turret.rs`, `misc_turret` and `misc_mg42`; the stock maps place `saw_bipod_*` guns on mp_backlot, mp_carentan, mp_convoy, mp_farm, mp_overgrown and mp_pipeline): the entity takes its arcs from its weapon (`leftarc`, `rightarc`, `toparc` and `bottomarc` in the map override them) and is a use target within `player_MGUseRadius` (128) for a player on the ground, holding no grenade, standing behind the gun within half its yaw arc. Holding use mounts it: `EF_TURRET_ACTIVE` goes in the player state with the weapon's stance, the movement keeps the view inside the arc (`viewAngleClampBase` and `Range`), the gun swings with the view (`gunAngles` in the entity state; clients turn `tag_aim`, `tag_aim_animated` and `tag_flash` by them), the gunner is held at the swung turret's `tag_player`, the attack button fires the weapon's bullets from the swung `tag_flash` along the view, and the crosshair shows the weapon's drop hint. Using again, dying, going down, respawning or disconnecting lets go (a living gunner gets their stance and place back). The gunner is placed from the swung `tag_player` rather than blended through the gunner animation, and `spawnTurret` (no stock script calls it) and non-bullet turret weapons are not implemented. Each round raises the turret's own fire event (`EV_FIRE_WEAPON_MG42`, naming the turret and the gunner) rather than a player's: clients play the muzzle flash at the muzzle (the weapon's first-person flash for the gunner), the weapon's `fireSoundPlayer` for the gunner and `fireSound` for everyone else from the muzzle, and shake the view of anyone within 100 units of the gun for 100 ms per round (`CG_FireWeapon`, `CG_StartShakeCamera`). Harness stage `net-turret`: two real clients on mp_convoy, one mounts a stock turret, is held in its arc, fires and lets go while the other is shown the gun, swung off its rest pose, and the gunner on it, and both receive the turret's fire event; `audio` asserts that the event plays the turret weapon's fire sound for the gunner and for a bystander, and `client-fx` that it flashes at the muzzle without a shell and shakes the view only within its radius. The gun's model (`weapon_saw_mg_setup`) names its material instead of defining it, as models of a map zone do for what `common_mp` defines; the client content resolves such names so the turret is drawn (client unit tests `a_stock_turrets_model_has_materials_to_draw` and `a_stock_turret_is_drawn`).

### Action slots, hardpoints and votes

`setactionslot(n, "weapon" name | "altmode" | "nightvision" | "")` fills one of the four slots of the player state; `+actionslot N` on the client selects the slot's weapon (pressed again, the one held before), toggles the alternate weapon or the night vision (an `altmode` slot raises the alternate fire mode of the weapon in hand, else of a primary the inventory holds, as the original's `CG_AltWeaponToggleIndex` reads the weapon last picked: the Assault rifle's slot key raises its underbarrel launcher), and the d-pad pieces (owner-draws 165-169) show them. The server now honours the weapon a person asks for (the weapon keys and slots). The killstreak UAV is earned into slot 4 by the stock scripts and called in by selecting it (harness stage `headless-hardpoint`: bots do it and the script's use is counted). The airstrike picks its target on the full-screen map: `beginLocationSelection` puts the selector in the player state, the mouse moves the point (owner-draw 186 draws the selector circle), the attack key confirms and the server answers `confirm_location` with the world point (`setMiniMap` supplies the map's size and north) or `cancel_location` (melee or reload); harness stages `headless-airstrike` (bots) and `client-hardpoint` (the real client: `+actionslot 4`, the d-pad pieces 166/168/169, the map pick).

The helicopter hardpoint runs on the stock scripts: `spawnHelicopter` makes a script vehicle that flies toward the goal `setVehGoalPos` gives it (speed, acceleration, yaw rate, pitch and roll limits, stops and hover as the original's AI move), a turret tracks `setTurretTargetEnt` and notifies `turret_on_target`, `fireWeapon` shoots its 20 mm bullets and homing rockets, and `G_Damage` on it reaches the script as `damage`, so it can be shot down (bots shoot enemy helicopters). `level.heli_paths` come from the map's `heli_start`, `heli_dest` and `heli_loop_start` entities. Clients are told of it as a vehicle entity. `spawnPlane` makes the airstrike's planes. Harness stage `headless-helicopter`: a bot calls it in, it flies, fires and is shot down. Not simulated: the body jolt when hit, the turret's moving barrel bone on the server (aim uses rest-pose tags), map collision for vehicles, hellfire and javelin guidance.

The client draws script vehicles (`VEHICLE` entities, the helicopters): interpolated between snapshots like the other players, the model's rotors turning with the `bh_rotors` animation (the rest of the model stays at its rest pose), the vehicle's sound loops following it and its weapon's fire sound and muzzle flash at the muzzle. Harness stage `client-heli`: a bot calls the helicopter in, the player is held behind and beside it every frame (`devheli view human`) and the picture must differ from the same view with `drawvehicles 0`.

The client draws missiles (`MISSILE` entities: thrown grenades, rockets, C4, claymores) as the weapon's projectile model along the entity's `angles`, with its trail effect pointing along the networked `velocity`, and loops the weapon's `projectileSound` on a missile in flight. An explosion event carries the surface it sat on: the client plays the impact table's blast and sound for that surface and then the weapon's `projExplosionEffect` and `projExplosionSound` (a flashbang or a dud has only its own); a missile that will not go off sends a dud event (`projDudEffect`, `projDudSound`). Harness stage `client-equipment` works the equipment from the player's keys: key 5 raises the Assault rifle's underbarrel launcher and a shot puts its shell in the air, and on Spec Ops the C4 is planted with the throw button (the pack shows on the ground and one is spent) and set off with the attack button (`PM_Weapon_CheckForDetonation` raises `EV_DETONATE`, which the scripts answer). `devgrenade <human|client> <weapon> [speed] [fuse_ms]` throws one for tests; harness stage `client-missile` asserts the model is drawn and the explosion is received and heard.

`callvote` and `vote` run in the server (`src/vote.rs`, the original's `g_oldVoting`): `map`, `typemap`, `g_gametype`, `map_restart`, `map_rotate`, `kick` and `tempBanUser` (which also refuses the address for `sv_kickBanTime` seconds, 300 by default) pass on a majority of the people playing (bots count as voters, spectators do not; an abstention weighs `g_voteAbstainWeight`, 0.5, when time runs out) and run three seconds later, or fail after 30 s; `g_allowvote` switches them off. Harness stage `net-vote` has two real UDP clients kick one of them and change the gametype and map. `map_restart` loads the level afresh with the latched `g_gametype` and `sv_maxclients` (so a gametype vote works), `fast_restart` restarts in place unless one of them changed, and `map_rotate` skips words it does not know and wraps. Across any level change the connected people keep their client slot and profile stats, and when the script left the level with `savepersist` (a round's `map_restart(true)` in Search and Destroy or Sabotage) their `self.pers` script array too, as the original hands each client's kept script array back to `ClientConnect` and frees it only without `savepersist` (`SV_MapRestart`, `SV_SpawnServer`, `G_ShutdownGame`); the stock `Callback_PlayerConnect` then spawns them on their team with their class instead of opening the team menu, and the attacker and defender sides swap as `sd.gsc` toggles `game["switchedsides"]`. Harness stage `client-sd-rounds` checks this through the menus on a listen server. `getinfo` carries `pswrd`, `ff`, `kc`, `hw`, `mod`, `pure`, `voice`, `pb`, `minPing` and `maxPing`, `getstatus` the server info and the players, and the configstrings `SERVERINFO`, `SYSTEMINFO` and `CODINFO` are published. Like stock `CG_ParseCodInfo`, the client applies every named `CODINFO` dvar after the complete initial gamestate and on later configstring changes; an absent value slot means an empty string. Our chunked gamestate carries an explicit `gamestate_end` reliable command (also emitted in demo initial state) so names arriving before their values cannot briefly clear `scr_allies` and make the scoreboard ask for `scorebar_`. `g_log` (`games_mp.log`) records `InitGame`, `ShutdownGame`, chat and the scripts' `logPrint` lines. A client's `userinfo` (name through `ClientCleanName`, `rate`, `snaps`) is read by the server, with `sv_maxRate` pacing; the client sends it on connect and the `name` command sends a new name. `g_inactivity`, the cheat/init/range rules of console variables, `pingPlayer` and the night vision notifies are in too. Voice chat and the talker icons (owner-draws 193-196) are not built: no voice is sent or played, and the pieces draw nothing.

The server console reads stdin, and with `rcon_password` set a UDP `rcon <password> <command>` runs the same commands with their output returned as `print` packets (1294-byte chunks; one request per 500 ms; bad attempts are logged). Operator commands: `status` (num score ping guid name lastmsg address qport rate; ping is `BOT`, `CNCT` or `ZMBI` when there is none to show; guid and rate are placeholders, this server has neither), `kick`/`tempBanUser`/`clientkick`/`tempBanClient` (the first and third by name or number; a brief ban of `sv_kickBanTime` seconds, or none for `onlykick`/`clientkick`), `banUser`/`banClient` (permanent, kept by address in `sv_banFile`, default `ban.txt`), `unbanUser <ip>`, `say`, `tell`, `systeminfo`, `dumpuser`, `toggle`, `reset`, `setfromdvar`, `cvarlist`; `heartbeat` only says there is no master server. Harness stage `net-rcon` drives them from a UDP socket. A client the server drops is told why (`Player kicked`, `Server command overflow`) and the others read `<name> left the game` / `was kicked` / `timed out`; a client that hears nothing for `cl_timeout` seconds (default 40) returns to the menu with `Server connection timed out`, and the `reconnect` console command rejoins the last server.

Network limits: the peer table follows `sv_maxclients` at each map start (a value latched in a cfg applies at the first `map`, and a later `set` replaces what is waiting, even when it gives the value already running). A client leaves with its sequence-checked reliable `disconnect`; a connectionless `disconnect` is ignored, so a forged one cannot kick anybody. Silence drops a client after `sv_timeout` seconds (default 240, at most 1800 as in the original) or `sv_connectTimeout` (45) if it never sent a packet since connecting. A client that has acknowledged a snapshot of this level and then leaves 29 or more (and 1.45 s worth) unacknowledged is sent them at a random, doubling spacing (up to 256 intervals of its `snaps`), and its scoreboard ping is the mean time it took to acknowledge the last 32 snapshots, at most 999 (999 while none were). A userinfo without `rate` or `snaps` gets 5000 B/s and 50 ms. `sv_maxRate` stays 0 (no server cap, a client rate of 25000 or more counting as 90000) because our snapshots are larger than the original's and its default of 5000 would pace them at a few a second; set it to opt in. Lag compensation covers up to 400 ms of lag (plus the 100 ms draw delay its time base already includes); a shot from further back is judged against the live bodies, as in the original. A closed or reloaded browser tab frees its slot when its WebTransport session closes. A client whose NAT changed its source port keeps its slot (matched by IP and qport); a `connect` from the same IP and qport frees the old session, and `sv_reconnectlimit` seconds (3) must have passed since it joined. `getchallenge`, `getinfo` and `getstatus` are rate limited per address outside the local network (16 burst, 8 a second) and for all addresses together; one `poll` reads at most 1024 datagrams; `sv_maxClientsPerIP` (0: no limit) caps clients per address outside the local network. `sv_privateClients` slots are only for a `connect` giving `sv_privatePassword` (which also skips `g_password`; `g_password none` means no password), `getinfo` hides the free ones, and `sv_minPing`/`sv_maxPing` refuse by the challenge round trip (local network exempt). Client commands are limited by `sv_floodProtect` (800 ms).

### Master server and the Internet list

cod4e keeps its own wire protocol, so it has its own master server: `cod4e-master [--port N] [--bind addr]` (UDP, default port 28950, no game files needed; run it on a public host and open that port). It is modelled on the stock flow (`SV_MasterHeartbeat`, the client's `globalservers`) in this game's out-of-band format.

The current protocol is **24**, which adds the initial gamestate's `gamestate_end` boundary. Demos and peers recorded or built with protocol 23 are incompatible and rejected with a message naming both versions, rather than leaving their CODINFO table incomplete.

- A server lists itself only when asked: set `sv_public 1` and `sv_master1`..`sv_master5` (`host[:port]`; all empty by default, so nothing is sent until you name a master). `cod4e-server` then sends `heartbeat <protocol>` every 60 s, and `flatline` when `sv_public` is turned off, a master is removed from the settings or it shuts down (`quit`, Ctrl-C or SIGTERM on Unix; a crash or SIGKILL sends nothing and the server expires in 180 s); the `heartbeat` console command sends one at once. The master names are looked up on a background thread (a failed lookup is retried after 15 s, a good one kept 10 minutes), never on the game frame. A listen server (started from the client's menus) never announces itself.
- The master answers a heartbeat with `getinfo <challenge>` to the address it came from and lists the server only when that address replies with the challenge, so a forged source cannot add a server or keep a dead one listed. The protocol it is listed under is the one its own `getinfo` answer reports, not the one the heartbeat claims. A `flatline` is checked the same way: the sender is probed and dropped when it does not answer, or when its answer says `public 0` (a dedicated server with `sv_public 0` says so); removing one master from a live server's settings only stops its heartbeats to that master, which then expires it after 180 s. A server with no verified heartbeat for 180 s expires.
- Clients ask with `getchallenge` and then `getservers <challenge> <protocol>`; the answer lists the servers of that protocol, 40 addresses to a packet (at most 320). The client then sends each server a `getinfo`, as its LAN scan does, and shows the ones that answer.
- Abuse limits: a per-IP and a global token bucket on heartbeats and on client queries, at most 8 servers per IP address, 4096 listed and 1024 being verified at once, and the challenge on both heartbeats and `getservers`. The buckets are keyed by the claimed source address, as any stateless UDP limit is, so someone forging a victim's address can use up its heartbeat allowance for a while; it cannot add, relabel or remove a listing.
- The client's Internet tab asks the masters in `cl_masters` (`host[:port]` words, up to five, looked up on a background thread; empty by default, and the tab then says no master is set, or that none could be found). Example: `set cl_masters master.example.org` in the client console, and `+set sv_public 1 +set sv_master1 master.example.org` on the server. Harness stage `net-master` starts a master, two public servers and a private one and checks that a client lists exactly the public two and that a stopped server drops off.

### Voice chat, demos and map downloads

Wire compatibility with the original is not a goal, so these are native designs (`net::voice`, `net::demo`, `net::download`). **Voice**: hold `+talk` (bound to `v` by default; `cl_voice 0` turns the microphone off) and 8 kHz mono audio goes to the server as 20 ms IMA ADPCM frames (33 kbit/s) inside the ordinary client packets; with `sv_voice 1` the server relays each frame as the original's `G_BroadcastVoice` does: to the speaker's team (everyone with `voice_global 1`, everyone when the speaker is in a free-for-all, and enemies in front of and within `perk_parabolicAngle`/`perk_parabolicRadius` of a player with Eavesdrop, `specialty_parabolic`), and only between players in the same session state (living with living, dead with dead, spectators with spectators) unless `voice_deadChat 1`, minus the players who muted the speaker. `cl_voice 0` also silences the voices the client receives (the mute menu sends `mute <n>` / `unmute <n>`), and flags the speaker `EF_TALK` (the talk balloon, script `istalking`). The browser build captures the microphone with `getUserMedia` into an AudioWorklet (a secure context and the person's permission are required; a refusal is printed once). **Demos**: `record [name]` / `stoprecord` write what the connection receives to `<config dir>/demos/<name>.c4edemo`; `playdemo <name>` loads the recorded map and plays it back on the recorded clock (`cl_freezeDemo 1` pauses). **Downloads and `sv_pure`**: with `sv_allowDownload 1` (off by default) a client that joins asks the server for its manifest (`getmanifest`: the mod's IWDs and zones, and the running map's zone, `_load` zone and IWD as `usermaps/<map>/…`, each with its size and CRC-32; the server serves those names and no others, and stock IWDs never) and fetches what it lacks or has a different copy of before joining (`cl_allowDownload 0` refuses). A mod goes to its `mods/<name>` folder and a map to `usermaps/<map>/`; nothing is written anywhere else, whatever the server lists, and a file whose size or CRC differs from the list is thrown away. A file of the same name already in the player's folder is replaced only when its CRC differs from the server's, and the client says so on its console; a link in the way of a write is refused. The list holds at most 64 files, 256 MB each and 2 GB together, with the map's files first; a server leaves out (and logs) what would pass that, and the client checks the disk has room before it starts. With `sv_wwwDownload 1` and `sv_wwwBaseURL "http://host/path"` (quote it: `//` starts a comment in the console; a tree laid out as `mods/<name>/…` and `usermaps/<map>/…`, as CoD4X documents) the client fetches over HTTP(S) instead (redirects are not followed, and the web server must be at the game server's own address or a public one, never a loopback, private or link-local address), and falls back to the server's own out-of-band `getfile` transfer if the web server fails or gives other bytes. Clients here always download before they connect, so `sv_wwwDlDisconnected` (accepted, as the stock cvar) changes nothing. The server's `sv_pure` (on by default for `cod4e-server` and for a server started from the menu, `+set sv_pure 0` turns it off; the library default is 0) refuses a `connect` whose IWD digest differs from its own: every non-localized IWD of `players`, `main_shared`, `main`, the map's `usermaps/<map>` and the mod folder counts, by name and by the CRCs of the files inside, so a changed or extra IWD is refused with a message saying so (the same list as the stock `sv_iwds`/`sv_referencedIwds` checksums, sent in one number). The join list's `ui_browserShowPure 1` (the stock default) lists only servers with `sv_pure 1`.

### Console, bind and menu commands

Every word a bind, a menu button or the console runs goes the original's way (`Cmd_ExecuteSingleCommand`): a command runs, a cvar's name shows or sets it, and anything else is forwarded to the server while in a match (which answers an unknown one) or called `Unknown command`; a menu's `exec` is never dropped (the stock menus' `updategamerprofile` and `uploadstats` are console commands the PC build does not register either, so they take that path as in the original). `cmd <words>` forwards its words as one client command (the Call Vote menus' Restart Map and Next Map use it); `mp_QuickMessage` (B) opens the quick message menu for a player in the game, whose keys answer through the stock scripts as team chat; `centerview` levels the view; `record [name]` and `stoprecord` write and end a demo (`demos/<name>.c4edemo`, the native format) with the stock messages; `setFromLocString` localizes a string into a cvar. Multiplayer has no pause: `cl_paused` is read only, and the stock Pause key's `toggle cl_paused` says so. The video options' Recommended button runs `configure_mp.csv` as `Com_SetRecommended` does (the CPU class is taken from the core count, not a benchmark), the language menu checks the selection against the languages the install has files for and restarts the renderer, and the PunkBuster and CD key buttons say they are not supported. The `client-commands` stage drives each of these as the player does and checks the effect.

On a listen server, the host's console also reaches the server's command table and registered dvars: `status`, `kick`, `clientkick`, `map_restart`, `fast_restart`, `map_rotate`, `serverinfo`, `cvarlist` and other server commands run on the server of this process and print back into the console. `set`/`seta` of a registered server variable (`scr_war_scorelimit`, `g_gametype`, `sv_hostname`, `g_password`, `bot_count`) reaches that server; words neither side recognizes are forwarded as client commands (`Server::host_line`, #366). The cheat client commands follow KisakCOD's CoD4 MP 1.8 `game_mp/g_cmds_mp.cpp` (`src/cheats.rs`): `give all|health [n]|weapons|ammo [n]|allammo <n>|<weapon>`, `take all|health [n]|weapons|ammo [n]|allammo <n>`, `god`, `demigod`, `notarget`, `noclip` and `ufo` require `sv_cheats` and a living player. A refusal is the localized `GAME_CHEATSNOTENABLED` or `GAME_MUSTBEALIVECOMMAND` game message, not a raw key; `kill` uses that same gate. `devmap <map>` enables cheats and `map <map>` disables them. `setviewpos x y z [yaw] [pitch]` requires cheats but not life, and puts the player's eye at the requested point; `entitycount` requires cheats and prints on the server console. Stock `printentities` and `visionsetnaked`/`visionsetnight <name> [seconds]` do not use `CheatsOk`; `mr` follows the existing menu-response handler. The default-suite `client-host-console` stage checks host `status`, `kick` and `map_restart`, six cheat refusals without cheats, and the enabled commands' state changes after `devmap` (#370).

### Mods and custom maps

`fs_game` (`+set fs_game mods/<name>` on the server, `--game mods/<name>` on the client; the folder must be one folder directly under `mods/`) puts `mods/<name>` on the search path above `main`, as the original does: its IWDs (every one, not only `iw_*`), then its loose files. The mod's `mod.ff` is loaded after the boot zones and outranks every other zone, the map's included. Fastfiles are looked up in the mod folder first, then `zone/<language>`, then `usermaps/<map>/`. Under a mod the server reads each script from the search path before the fastfiles (`Scr_ReadFile`): a mod's loose or IWD `maps/mp/gametypes/*.gsc` replaces the stock script of that name or adds a new one, and so does `main_shared`. Scripts with the CoD4X `.gsx` extension are not read (no CoD4X compatibility). The client's mods menu lists the folders of `mods/` (`description.txt` or the folder name); `RunMod` sets `fs_game` and restarts the menus on the mod's `mod.ff` (menus, fonts, strings, materials) and IWDs, `ClearMods` goes back to stock. Joining a server that runs a mod makes the client run it too (the server's `game` info key; a mod the install lacks is downloaded first, see Downloads). A listen server (`--listen`, or the menus) runs the client's mod.

An asset one zone stores as a name behind a comma (`,gfx_smk_white_atlas`) is a reference to the asset of that name a zone loaded before it defines; the zones are decoded in load order into one table per consumer (`assets::zone::Db`, the original's `DB_LinkXAssetEntry`), and such a reference becomes that definition as it is decoded, so a map's effects draw the smoke, fire, mist and glass sprites and the model materials `common_mp` defines, and a map's props and weapons use the models and effects of the zones before them. A later zone's definition shadows an earlier one's of the same name when its rank is at least as high (the boot zones below a map, `mod.ff` above all), and when a map or a mod is unloaded its definitions leave the table and the ones they shadowed are in use again (the original's override chain). When no loaded zone defines the requested asset, the linked loader silently creates an entry under the requested name using the type's lowest-ranked stock default (`DB_CreateDefaultEntry`; materials use `$default`, models `void`, effects `misc/missing_fx`; a sound's alias list is cleared). The renderer therefore draws the stock default for missing `mc/lambert1`, rather than dropping its draw. If the type's default itself is missing, loading fails, as the original does. The menus, the renderer's technique sets and the sound bank resolve by name as well, which also covers the case the table cannot patch retroactively: a reference stored before its definition (a menu icon only a weapon defines), which the original fills in later in place.

A custom map made with the stock tools lives in `usermaps/<map>/` (`<map>.ff`, `<map>_load.ff`, `<map>.iwd`); its IWD is on the search path while that map runs, it is listed with the maps of the server settings, and a server with `sv_allowDownload 1` gives all three files to clients that lack them (see Downloads).

### Browser clients (WebTransport)

`--webtransport [host:]port` (cvar `net_wt`, empty = off) also serves WebTransport next to UDP: a browser sends and receives the same datagrams as a UDP client (connect packets and netchan), peers named by their QUIC address. A datagram up to the session's maximum datagram size (capped at 1200 bytes, the browsers' limit) is one WebTransport datagram; a longer one, up to 8192 bytes, is one unidirectional stream carrying exactly those bytes, ended by FIN; both forms are accepted in both directions (`net::wt` module docs). Anyone may connect; bans, rate limits and the password apply to the connect packets as for UDP.

Without `--wt-cert cert.pem --wt-key key.pem` (cvars `net_wt_cert`, `net_wt_key`) the server makes an ECDSA P-256 certificate valid 13 days at each start and logs its SHA-256 (base64 and hex). With `--wt-info file.json` (`net_wt_info`) it writes what the page needs for `new WebTransport(url, { serverCertificateHashes: [{ algorithm: "sha-256", value }] })`: `{"url":"https://localhost:4433/","certHashSha256Base64":"..."}` (`localhost` when bound to every address, which includes IPv6; a loaded certificate has no hash field). The page decodes the base64 to the 32-byte `value`.

```sh
COD4_PATH=/path/to/install nix develop -c just server --webtransport 4433 --wt-info wt.json +map mp_crash
```

## Playing

`cod4e` with no options starts in the stock main menu, drawn from the install's own menu assets (`ui_mp`/`common_mp` menus, fonts, localized strings and images; `src/ui`). Mouse and keyboard drive it like the original: Start New Server picks a map and gametype and starts a listen server (alone unless the `bot_count` setting, archived and 0 by default, asks for bots: set it in the console, and it is read at every map start; `bots <n>` in the console sets it and changes the bots of a server started from this client at once; `--bots <n>` overrides the setting), Join Game takes a server (its list is the LAN, the internet or the favorites, cut to a game mode; the line above it says how the refresh is going; Server Info shows the selected server's settings and players from a `getstatus` query), Options and Controls edit the dvars and binds (click a key slot, press the new key; Backspace clears it; the choices survive in the config file). The default binds are the install's own `default_mp.cfg` (read from its archives, as the original does), then the profile's `config_mp.cfg`; only keyboard look, the mouse wheel and gamepad binds are added by the client, Esc opens the in-game menu. The 640x480 menu space is anchored to a 16:9 safe area at any window shape. `--ui-tour <dir>` opens the menus one by one with no world and saves a screenshot of each (harness stage `client-ui`); `--ui-script click=Start New Server,menu=createserver,click=Start,ingame,shot=a` drives them like a player.

A map loads in the background: one thread decodes the zone, uploads the world and builds the renderer with all its pipelines (on half the cores) while others decode the client content and boot the listen server, and the window keeps presenting the map's `loadscreen_<map>` picture with a progress bar (Esc cancels). The load prepares, per material, the scene chains (lit, sun, spot, omni, down to emissive and unlit) and, only where the material's techset has the slot, the optional passes (shadow map, shadow cookies, dynamic lights, floatz), as the original asks a material for those techniques only where it has them (`MTL_GAMEFLAG_CASTS_SHADOW`, the light surface lists); a stock techset without one of them casts no such pass and is not a warning. A material with no scene technique at all logs `no usable technique` and the log gate fails the stage. A warm-up frame primes the renderer and the player models, so the first frames in the world do not stall either. The models the server precached beyond those (planes, vehicles, props the scripts make) arrive as configstrings once connected; the original registers them under its load screen (`CG_RegisterGraphics`), here their passes are prepared a few per frame (aiming at 2 ms; one model's passes can take up to 16 ms in one frame on the Linux test host, #457) and their pipelines compiled on the worker threads, so a frame never prepares a whole list at once (it cost one frame 31 ms). Harness stage `client-load` asserts the longest gap between presented frames during the load stays under 100 ms on `mp_crash` and the largest map.

In a match the stock HUD menus are drawn with the client's own owner-draw pieces (`src/ownerdraw.rs`): the magazine graphic and reserve, weapon name, grenade counts, the sprint meter, the low-health overlay with the original's pulse phases (`hud_healthOverlay_*`), the hold-breath, mantle and no-ammo hints, and the corner compass with the level's map image (`setMiniMap` and `northyaw`, `src/compass.rs`): it scrolls with the player and turns with the view, shows teammates and, for a couple of seconds, enemies that fire, marks helicopters (owner-draw 155; the stock menus only place it in `compass_old`, so a menu that uses it is needed to see them) and airstrike planes (156, `PLANE` entities from `spawnplane`) with friendly or enemy icons by their owner's team, sweeps a radar line across the map while `setteamradar` or `hasradar` gives the player radar (`ps.radarEnabled`, `compassRadarUpdateTime`) and shows the enemies the sweep passes for `compassRadarPingFadeTime`, and the full-screen map used while picking an airstrike location. The `hud_fade_*`, `hud_enable`, `compass*` and `cg_draw*` dvars apply. Health reaches the client in the player state, so the bar (`cg_drawHealth`) and overlay follow the server. Not done: use-trigger cursor hints (the server does not yet say what the crosshair is on), the d-pad action slots and the talker icons.

```sh
COD4_PATH=/path/to/install nix develop -c just client --listen --bots 9   # solo: a team deathmatch against bots
COD4_PATH=/path/to/install nix develop -c just client --connect host:28960 # a `cod4e-server` (set net_port; default 28960)
```

The client talks to the server over UDP (`net`: sequenced, fragmented netchan, delta-coded snapshots about 36 per second, up to 3 usercmds per packet with redundancy). `--listen` runs the same server inside the client process. The player's own movement is predicted with the very `sim::pm::run_usercmd` the server runs (other players are collision boxes from the snapshot; server corrections fade over 100 ms, a teleport shown as one; the server's `g_speed` and non-stock movement and weapon dvars such as `jump_height`, `friction` and `player_meleeRange` reach the client in a configstring; own footsteps, jumps, landings and shots are played from the predicted events, once each however often the replay raises them); other players are drawn 100 ms behind the server clock between two snapshots, and the server rewinds them to that moment when it judges a shot (`g_lagcomp`, at most 250 ms back). Keys, mouse, gamepad and the config file are the input layer's (`bind w +forward`). In a match the mouse is locked whenever no menu is open (no click needed after a menu closes); Esc with no menu to open releases it (it never quits) and a click takes it again. `COD4E_INPUT_DEBUG=1` prints one `input:` line per second to stderr: events per second from GCMouse and winit, which source feeds the look, the GCMouse devices and whether our handler is on each, window focus, pointer lock, and how many frames of motion the focus/lock gate threw away.

Stage 4 (`client-match`) is the real client with `--listen --autoplay`: a scripted player walks toward and shoots the bots for 90 seconds. It asserts connected and spawned, walked, saw the bots, prediction rarely corrected, the view model drawn, every `script_model` the server published drawn, no magenta in the last frame, no stretched skinned triangles, no script errors, no frame that compiles a pipeline itself, no frame that prepares more than 64 material passes itself (a precache list taken in one frame) and no frames far over the median cost (a hitch), shots fired and their impacts, muzzle flashes and pain reaching the client as events and effects (hit registration is the server tests' job, not this stage's, which runs under host load); it reports bandwidth, snapshot rate, frame times and the server's tick cost. `frames.raw.csv`'s `cpu_ms` is the frame's whole work (input, the network frame, the warm-up, the render, the UI and the present) without the wait for the surface texture, and `frames.phases.csv` says where each frame went; when the frames hitch the failure lists the phases that held the excess and the worst frame's, and says whether one phase held the stalls (a call the client blocks in) or every phase stretched alike (the process not being scheduled: the machine, not the client). It needs a display and skips without one. `net-loopback` and `net-match` cover the protocol and 4 clients with 12 bots without a display; `net-ui` plays the menus a person would (team, class) against Domination and checks the hud elements, objectives, configstrings, client dvars and print lines the stock scripts send (`net::ui` is the client-side contract); `net-killcam` has a bot kill the client and checks the stock killcam replays the killer's view from the server's state ring and ends. `net-perks` has two UDP clients upload profiles with custom classes and checks the perk bits, grenade and ammo counts, the Juggernaut, Stopping Power and Sonic Boom damage numbers, Last Stand (pistol only, crawl, the health written back to 1 by `lastStandKeepOverlay` within its cycle whenever the stock regeneration adds to it, ten second bleed-out credited to the attacker, and a grenade kill on a Last Stand class dying at once) and Martyrdom's dropped grenade; the hits come from the `devkill <victim> <attacker> [damage] [mod] [weapon]` console hook, which runs `G_Damage` and the scripts' damage callback.

Stage `client-dedicated` is the portable folder's way to play: the real `cod4e-server` binary (next to the harness, or `COD4E_SERVER`) on a free UDP port with `bot_count 3`, and the windowed `cod4e` client joining with `--connect --autoplay` for 45 seconds. It asserts connected, spawned, moved, fired, snapshots arriving, prediction rarely corrected, no pipeline built mid-play and no clock jumps (the share of hitching frames is reported as a metric, not gated: `client-match` gates it, and here the server and the host's other load compete with the client), and then that the server's `status` no longer lists the player and logged that it left the game (a clean disconnect, not a timeout).

The client draws what the original's cgame draws over the stock HUD menus (`src/hud`): the script hud elements (text, values, timers, materials, clocks, waypoints with an off-screen pointer, with their alignment, move, fade, scale and glow), the `iprintln` and kill-feed message windows (a message is the original's key-and-arguments string: the first localized key, then each argument fills the next `&&1`, `&&2`; the stock `gamemessages`, `boldgamemessages` and `subtitles` menus place them), team-coloured kill lines with the weapon's kill icon, chat, the centre string, the scoreboard rows under the stock top bar (hold Tab; rows ask the server every 2 s), the killcam (the stock `killcam` menu is shown while the server replays a kill) the name of the player a spectator follows with the key help for following (`cg_descriptiveText`; a spectator who follows nobody flies freely, the server running the movement at speed 400 when the scripts allow `freelook`), teammates' names over their heads with the rank icon (fading with distance and line of sight; `cg_drawFriendlyNames`, `cg_overheadNames*`), the name of the player under the crosshair (`cg_drawCrosshairNames`, `cg_enemyName*`/`cg_friendlyName*` fades) and head icons from the scripts' `headicon`/`headiconteam` (bomb and flag carriers) with the connection-interrupted and killcam "you" markers (`cg_scriptIconSize`, `cg_headIconMinScreenRadius`). Harness stage `client-hud` plays a bot match, holds the scoreboard and waits for a kill, and checks what the HUD drew (`hud_draw` in `ui-script.json`, including the overhead and crosshair names; `--ui-script` also takes `scores=on|off` and waits `killcam|dead|intermission|feed`).

A match started from the menus runs on to its end: the scoreboard stays up until the server rotates the map, and the client then loads the next map in the same process (the server's `map` command carries the level; the connection and the player stay), returning to the team and class menus. Start New Server rotates through the stock maps after the chosen one and passes the `scr_*` dvars the player set (time and score limits) to the server, which takes a standard port (28960-28963) when one is free. Join Game asks the server (`getinfo`) which map it plays before loading anything, so a typed address or a listed server joins the right map; its list shows LAN servers (a broadcast and loopback `getinfo` on the standard ports; Refresh List rescans) and favorites (Create Favorite with an address, or Add Favorite on a listed server; kept in `<config dir>/favorites.txt`, one `address:port` a line, at most 128 (lines that are not an address, such as a host name, are kept as written), where the stock game dumps its structs into `servercache.dat`). The Filter popup's settings (`ui_browserShowFull`, `ShowEmpty`, `ShowPassword`, `ShowPure`, `ShowDedicated`, `Mod`, `Friendlyfire`, `Killcam` and `ShowPunkBuster`; `ShowPure` is the stock default 1, which the popup has no control for, so it lists only `sv_pure` servers) cut the list as in the stock browser, and every column header sorts it. A passworded server shows an X in the first column; the Password button, or the `password` dvar, sets the password a join sends, and joining such a server with none set opens the Password popup first, and a refused join (wrong password, full server) returns to the menus with the reason, asking for the password again if it was wrong. Every other failed load or join ends the same way, as the original's `Com_Error(ERR_DROP)` does: the session ends, the main menu comes back and the stock error popup (`error_popmenu`, `com_errorMessage`) names the reason: a map change to a map the install lacks (`Could not find zone '<zone>'`), an address nothing answers, a connect the server never answers (20 s), a server that goes silent for `cl_timeout` (40 s) and a kick with its reason; `reconnect` from there rejoins the last server. A `map` or `devmap` of a map the install lacks starts nothing, as the original's `SV_Map_f` checks the zone first, and shows `Can't find map "<name>".` in the same popup (the original prints that line to the console only); typed during a match it leaves the match running, and a bare `map` does nothing. Harness stage `client-error` drives each through the console and asserts the popup and its text. Stats (rank, unlocks, class setups: the menus' `stat(n)`) belong to the player profile: the profiles of the install's `players/profiles/<name>/mpdata` are listed in Select Profile next to the user's own (`<config dir>/players/profiles`), `active.txt` names the one used last, and New and Delete work (the install is only read: a changed profile is saved to the user's folder, as a decrypted `mpdata` (the CoD 4 X `ice0` form); see the paragraph below for the original's encrypted `iwm0` files). The client loads it at start, uploads it to the server when it joins a level, and takes the server's later `setstat` changes back into it.

Player profiles (rank, unlocks, custom classes) are read from the install's `players/profiles/<name>/mpdata`, in either format: the stock game's encrypted `iwm0` file and CoD 4 X's decrypted `ice0` file. An `iwm0` file is opened with the key the original derives from the install's CD key (`codkey` in the registry on Windows, or in the `system.reg` of the Wine prefix named by `WINEPREFIX`, else `~/.wine`, elsewhere) and is rejected when its hash does not match, as the original rejects it (without the key the profile is listed and starts fresh, with a message on stderr; the key is never printed or stored). Everything the client saves goes to its own copy under the config folder (`--config` moves it), in the `ice0` format, and shadows the install's profile; the install's profile is never written, so the stock game keeps reading it unchanged.

Every windowed harness stage runs the client with `--config-dir <stage dir>/config --harness-profile`: the folder gets a fully unlocked profile `harness` (all perks, weapons and attachments, Create a Class open, top rank; kept if it exists, so a stage's own saves carry into its next run) and only that profile is listed, so a run never loads the tester's or the install's profile (the stock main menu asks which to use when several are listed). The headless stages `headless-sab-objective` and `headless-airstrike` do not wait for bot luck: idle bots (`bot_idle`, which hold `+activate` under a use trigger's hint) are placed with `devtele` and `devrun <seconds>` runs the server between steps, and the airstrike is handed out with `devhardpoint` as in `headless-helicopter`.

Harness stage `client-sd-rounds` starts a three-round Search and Destroy from the menus, with the sides switching every round, and after each round restart asserts the player spawns again on the same team with no team menu, that the server's objective text names the other role in round two and the first one again in round three (the sides do not switch after the last round), and that the team survives into the final scoreboard. Harness stage `client-menu-match` runs the client with no flags and a `--ui-script`: Start New Server with a three-kill score limit, team, class, the end-of-match scoreboard, the rotation into the next map, then team and class again and a second spawn. It needs a display and skips without one. Harness stage `client-custom-class` plays from a custom class with a profile's stats: the P90 in the class spawns, the profile's perk and experience stats survive the join, a class change in the grace period applies and every other player is drawn (the client sends its profile right after connecting and the server holds `begin` until it has it, as the original holds the game state until the stats are in). Harness stage `client-ingame-menu` changes team and class mid-round through the in-game menu with `mouse=` clicks and checks that Escape and every pick return to the game, the team changes and the new class spawns, and that each menu lists the stock items (`see=` and `nosee=`). Harness stage `client-frontend` opens the main menu, Select Profile and Create a Class with the install's own profile, steps the game mode chooser (`mouse=#245`, `cvaris=`) and checks that the install's `players/` folder is unchanged. `--ui-script` also has `mouse=<item>` (a click through the pointer), `key=escape`, `nomenu`, `team=<n>|save|other|same` (`other` is the opposite side, 1 or 2: a spectator or a dead player is on neither), `weapon=<name prefix>` (`m16_gl` is the rifle, `gl_m16` its launcher raised), `holdkey=<key>` and `releasekey=<key>` (a key the config binds; an unbound key fails the step), `throw=<key>[:secs]` (presses, lets go after 0.6 s, then needs the grenade count to drop, a missile entity to appear and the player alive, so a frag cooked off in the hand is not a throw), `set=<console line>`, `connect=<host[:port]>`, `stat=<index> <value>`, `statis=<index> <value>`, `map=<name>[:secs]` and `maprotate[=secs]` (waits for a loaded map first and reports `<from> -> <to>`, both map names) steps. Each waiting step keeps its own state, so a `team=save` cannot stand in for the map a rotation started from.

The graphics options take effect: Apply runs `vid_restart`, which moves the window (`r_mode`, `r_displayRefresh`, `r_fullscreen`, and `r_monitor`, the 1-based monitor fullscreen goes to, 0 automatic; windowed stays on the monitor it is on, and the mode lists are the chosen monitor's; `--monitor <n>` at start; exclusive fullscreen is borderless on Wayland, which has no mode switch), sets the present mode (`r_vsync`; a `--present` choice wins) and the screen shape (`r_aspectRatio`, which sets the projection's aspect), and changes a running match's antialiasing (`r_aaSamples`, up to 16x multisampling of the scene pass, stepping down one sample at a time to what the device offers), shadows (`sm_enable`), the sun's specular (`r_specular`), depth of field (`r_dof_enable`) and glow (`r_glow_allowed`). Brightness (`r_gamma`, default 0.8) works as the original's display ramp does: it maps the whole picture through `pow(x, 1 / r_gamma)` only in full screen (exclusive or borderless) and not with `r_ignorehwgamma 1`; a window shows the picture as drawn. `r_distortion` switches the heat haze and shockwave materials, which sample a copy of the scene taken before the emissive surfaces; soft (z-feathered) particles fade where they meet geometry. `r_zFeather` off draws soft smoke with hard edges, and `r_drawWater` off freezes the water's motion. Pixels nothing draws (a camera inside a wall or outside the sealed world, a view past the map's edge) are black, as the stock engine shows them: its colour buffer is cleared only as `r_clear` says (`R_GetClearColor`; the shipped default `dev-only blink` never clears without `developer`, so the target keeps what it held, black on the reference host, and a stale frame is nothing to copy) and never to the fog colour. `r_clear` (`never`, `dev-only blink`, `blink`, `steady`, `fog color`, by name or index), `r_clearColor` and `r_clearColor2` (`r g b a` in 0..1, blinking every 512 ms) are read with the other graphics dvars at map load and `vid_restart`. Harness stage `client-clear` holds the client at the #356 viewpoints on mp_crash and mp_backlot and checks the undrawn regions are dark and the walls are not. Texture size (`r_picmip` for colour maps, `r_picmip_bump` for normal maps and `r_picmip_spec` for specular maps, all with `r_picmip_manual`) and anisotropic filtering (`r_texFilterAnisoMax`) apply to the next map that loads. `com_maxfps` (stock default 85, 0 to 1000, 0 for no cap) paces frames in whole milliseconds (`1000 / com_maxfps`) with `r_vsync` 0 only. Unlike stock it is not applied while vsync is on: the display paces the frames, and a cap below the refresh rate (85 on a 120 or 144 Hz screen) would give an uneven cadence. `cg_drawCrosshair 0` hides the crosshair, `ragdoll_enable 0` leaves corpses in the pose their death clip ends in, and `fx_marks 0` hides bullet holes and blood marks. `r_rendererPreference`, `r_multiGpu` and `ai_corpseCount` are kept for the menus only: they choose a Direct3D 9 code path, an SLI/Crossfire mode and the corpse cap of single-player actors, none of which exist here. The HUD layout dvars (`cg_hudVotePosition`, `cg_hudSayPosition`, `cg_hudChatPosition`, `con_gameMsgWindowN*`, `cg_hudDamageIcon*`, `cg_scoreboard*`) are read as the stock cgame reads them. The saved choices apply at start unless `--size`, `--refresh` or `--fullscreen` was given. `r_vsync` starts at 1 here, not the stock 0. Harness stage `client-gfx` sets them in the menu, applies them with `vid_restart`, starts a match and turns them back, checking the surface's and renderer's own state each time.

`screenshotJpeg` (the stock F12 bind) and `screenshot` write the frame as `shotNNNN.jpg` / `shotNNNN.tga` into `screenshots/` of the user's folder (`screenshot <name>` names the file, `silent` prints nothing). A gamepad button can be bound from the Controls menu: while an item waits for a key, the next pad button is the binding (Start cancels). Not done, on purpose: `cinematic`, `unskippablecinematic` and `logo` print "not supported (Bink video)" (the stock videos are Bink and there is no decoder we may use, so the startup intro does not play); the `screenshot levelshot` and `screenshot savegame` forms do nothing; a screenshot name with a path separator or `..` is refused, so files stay in `screenshots/`; gamepad rumble, aim assist and glyphs are IW3x extras, not stock.

The view follows the original's cgame beyond first person: a dead player sees their body from behind, turned the way the blow came from (`cg_thirdPersonRange`, `cg_thirdPersonAngle`, a collision trace keeps the camera out of walls), and a killcam whose script named a killing entity hangs the camera on it (helicopter or airstrike views with their own field of view and blur). Depth of field comes from the player state: `setDepthOfField` / `setViewModelDepthOfField` write it (the stock scripts call it at every spawn), and with no scripted range the sights blur the near and far field around what they point at. Fog is the server's: `setExpFog` publishes it in a configstring and clients blend to it over the transition time; the createart text scan only serves the viewer modes with no server.

## Browser

The `client` crate also builds for `wasm32-unknown-unknown` (`web/`): one build, WebGPU when the browser has it and WebGL2 otherwise (`--backend` / the page's Graphics choice overrides; the F3 overlay shows the backend, frame times and memory). The page reads your install in the browser and never uploads it: pick the install folder (or drop it); with "keep a copy" on, the files the client reads (about 4 GB) are also saved in the browser's private storage (OPFS) so the next visit needs no pick. The wasm runs on the page's main thread and reads the install synchronously through a reader worker (`web/reader.js`, shared memory), so the page needs cross-origin isolation (COOP and COEP headers; `web/serve.py` sends them).

```sh
nix develop -c just web-build          # wasm-bindgen + wasm-opt into web/pkg
nix develop -c just web-serve 8080     # then open http://localhost:8080/
```

For automated runs `web/serve.py --install <dir>` also serves the install files under `/install/` (development only, never on a public host) and `?dev-install=/install&autostart` makes the page use them without a picker; `?flythrough` flies the camera, `?report=N` posts the overlay values to the server log after N frames. In the browser the pipelines are built a few milliseconds per frame (WebGL2 links shaders serially, 3232 of them on `mp_crash`) instead of all before the first frame: draws whose pipeline is not ready yet are skipped (the F3 overlay shows pipelines built and draws skipped), and `?args=--fly-at 3` holds the flythrough at a fixed time so pictures compare across builds. Harness stage `web-client` does this with a headless Chromium when one is found (`COD4E_CHROME`) and skips otherwise. Harness stage `web-join` starts a native server in the harness (WebTransport on a free port, nine bots in a team deathmatch on mp_crash, certificate hash from `--wt-info`), loads the page with `?connect=127.0.0.1:<port>&cert=<hash>&args=--autoplay --duration 100000`, and waits for the page's report 15 frames after the server put the player in the world (`?report=N` counts from the spawn when `?connect` is given). It passes when the page's `net phase` overlay field (`connecting`, `connected`, `spawned`) says `spawned`, snapshots arrived, surfaces were drawn, and the server itself lists a person (not a bot) playing; it records connect time, snapshots, page CPU ms, wasm memory and frames. It runs `web/serve.py` with `python3` from the PATH (the devshell's), and skips like `web-client`.

`client-fx` runs `cod4e --fx-selftest` (no display, no GPU, the install needed): on mp_crash an explosion draws sprites and then ends, a bullet into the floor plays its impact effect, a shot plays its muzzle flash and ejects a shell that falls under `phys_gravity` and comes to rest, and the vision and shell shock files the stock scripts name are in the install and change the picture. Effects are drawn from server events: impacts, explosions, flesh, `playfx`, and a weapon-fire event for the flash (bolted to the gun's `tag_flash` and `tag_brass`, first person and third, following the gun while they play; a bolt-action throws its shell on the rechamber, and the last round of a clip has its own). Each bullet shot is a tracer with the client's `cg_tracerchance` (0.2; `cg_firstPersonTracerChance` 0.5 for the player's own), drawn as a corkscrewing beam in `gfx_tracer` that flies from the muzzle to what the shot's aim meets within 8192 units (`cg_tracerScale*` widen far ones); the selftest asserts a burst of five fired shots draws five beams, and that every sprite, decal and model material of every effect in the loaded zones is defined in full (none is left a reference to another zone's, #453). A knife blow announces what it struck (flesh or world, for the stock melee sounds and the blood on the attacker's knife), and a swing at an enemy near the middle of the screen lunges at them and pulls the view onto them (melee aim assist). Dead players leave a corpse entity (`clonePlayer`) that every client draws as a joint-limited rigid-body ragdoll (the install's `ragdoll.cfg`: capsule bones, hinge and ball joints with angle limits, limb self-collision) that blasts wake and throw and the map's clutter props are thrown by shots and blasts and effect models with `USE_MODEL_PHYSICS` (brass, debris) and models the script `physicslaunch`ed are PhysPreset rigid bodies (mass, bounce, friction, the model's physics geometry; each client's own simulation, on the map's collision, not shared); `visionsetnaked`, `visionsetnight` and `shellshock` reach the client as commands and drive the glow, film and saved-screen overlays (a shell shock also ducks the sound by channel, fades in its room reverb, rings its tinnitus with end stings and caps how fast the view may turn); the night vision goggles (`n`) blend to the night set. `--fx-demo <effect>` plays one effect in front of the camera every 1.5 s of a `--listen` run.

`client-viewmodel` runs `cod4e --viewmodel-tour 20` on mp_backlot, mp_crash and mp_strike (a GPU adapter and the install needed, no window): the first-person M16 and hands are drawn headless from the spawn points and from points on the way between them, with and without, and the pixels they change must not be dominated by one colour channel and the spawn views must be neither black nor blown out. It guards the reflection probe of moving models, which follows the original's `R_CalcReflectionProbeIndex` (the nearest probe of the cell holding the model, never the solid-red default probe 0 unless the cell has no other); a nearest-anywhere search once picked the default probe near the map's centre and painted the gun red.

Water materials animate with an ocean simulation (`--fx-selftest` checks that the surface moves and spreads on mp_farm's puddles); projectiles in flight play their weapon's trail effect, and trail elements draw as ribbons through the points the effect passed (the selftest flies a rocket and checks that the strip draws and ends). The portal walk clips at the eye rather than the near plane, so a doorway beside the camera no longer hides the view beyond it (mp_crash's alley). The remaining unknowns are settled as follows: mp_bog's blocky facades are the original's nearest-filter, no-mip sampler state, and `iw3mp.exe` writes `D3DRS_SRGBWRITEENABLE` as 0 with no sRGB sampler read found, so textures stay sampled as plain unorm.

`just map-sweep <cod4e> <install> <out> [seconds]` (`scripts/map-sweep.sh`) plays every stock map in war, dm, dom, koth, sab and sd with the windowed client (`--listen --autoplay`, five bots) and prints one table row per run (spawned, bots seen, shots fired by anyone, script errors, missing effect/vision/shock files); a run in which nobody fires is repeated at three times the length and fails if it still stays silent (big maps need a while before bots meet). `just slot-exec` runs it on the Linux test host with a display.

Controls in the page: click the game to lock the mouse (Esc gives it back and opens the menu; the page drops the lock on its own when the browser takes it, and the next click locks again), F11 or the `togglefullscreen` command switches fullscreen (the canvas and the field of view follow the new size), and a gamepad works through the browser's Gamepad API (`gilrs`; the same binds as native). F3 toggles the overlay, which also shows the view, the pointer lock and the sound output (`running`, `frames_played`, `underruns`, `buffered`, `peak`, `shared`). Sound starts with the page; until the AudioContext is allowed to run (a click or key) frames_played stands still and "Click to enable sound" shows. The sound tables load on the main thread in the browser (a one-off stall at the map load, which counts as underruns).

What the browser keeps: the settings and binds are written as a `config_mp.cfg` per profile to the browser's `localStorage` (key `cod4e:players/profiles/<profile>/config_mp.cfg`) two seconds after they change, and read back at the next visit, so a tab needs no exit to save them (the window size and fullscreen are the page's and are not kept). The install's language is line 1 of its `localization.txt` (default `english`): the page reads that language's `zone/<language>` folder, so a non-English install works as it does natively. Joining a server whose map (or mod) the install lacks fetches it first when `cl_allowDownload` allows (the page's connect field, `?connect=`): the client asks the server's manifest over the WebTransport session, downloads the files it lacks (checked by size and CRC-32), mounts them in the install it reads and has the page keep them in the browser's private storage (`cod4e-downloads`, next to the saved install copy), so the next visit has them; "Delete the saved copy" removes both. The fast-download web server (`sv_wwwDownload`) is not used by the browser: its fetch needs CORS headers on that server, so the browser takes the files from the game server. The graphics menu's resolution list holds the sizes that fit the screen: a windowed choice resizes the canvas, fullscreen takes the screen (the browser grants it only right after a click or key press); the browser gives no say over the refresh rate. Harness stage `web-download` joins a server whose custom map the browser lacks, then opens the page again and checks it downloads nothing.

## Layout

| crate | role |
|---|---|
| `assets` | VFS, IWD, fastfile decoding, IWI, typed assets |
| `gsc` | GSC compiler and bytecode VM |
| `sim` | collision traces, player movement, weapons |
| `net` | netchan, snapshot delta codec, transport trait |
| `server` | match simulation and `cod4e-server`; no GPU, window, or audio dependencies |
| `master` | `cod4e-master`, the master server: the list of public servers (no game files needed) |
| `sm3` | D3D9 SM3 bytecode to WGSL |
| `render` | wgpu renderer |
| `audio` | ordered-zone sound alias tables (including name-only sample references), realtime-safe mixer (`Mixer::fill`, AudioWorklet-ready), WAV/MP3 decoding, cpal output (AudioWorklet in the browser) |
| `client` | `cod4e`, the player-facing client (native, and wasm for `web/`) |
| `harness` | `cod4e-harness`, scenario runner and run bundles |
