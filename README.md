# cod4-decomp

A GPL-3.0-only Rust reimplementation of the Call of Duty 4: Modern Warfare (1.7) multiplayer engine. It runs on macOS, Linux, and Windows, and includes a headless server. It contains no game content: you supply your own copy of the game.

Planning and decisions: [wayfinder map](https://github.com/jeiang/cod4-decomp/issues/1). Terms: [CONTEXT.md](CONTEXT.md). Decisions with lasting effect: [docs/adr](docs/adr).

## Build

```sh
nix develop -c cargo build --workspace
nix develop -c cargo test --workspace
```

Without Nix, install rustup; `rust-toolchain.toml` selects the toolchain.

## Original install

The engine reads a CoD4 1.7 install directly: `main/*.iwd`, `zone/<language>/*.ff`, and `localization.txt`. Set `COD4_PATH` to the install directory. The default is `./COD4`, which is gitignored. Never commit or upload anything from the install. Tests that need the install skip when it is missing.

## Harness

`cod4e-harness` runs the staged suite under a watchdog (each stage in a child process; crashes, hangs and panics are caught) and writes `cod4e-run-<date>.zip` (at most 100 MB, user and host names scrubbed) with `manifest.json`, `summary.json`, logs, CSVs, a Perfetto-readable `trace.json` and minidumps.

```sh
nix develop -c cargo run --release -p harness -- run --out bundles   # default suite
nix develop -c cargo run --release -p harness -- stages              # list stages
nix develop -c cargo run --release -p harness -- diff a.zip b.zip    # compare two bundles
```

Stages that need engine commands read console scripts (`scenarios/*.cfg`, or `--script file`); commands the engine lacks yet are reported as skipped. Double-clicking the program runs the suite with the zip next to it. The CI `windows` job uploads that portable folder and smoke-tests it with no install. `scripts/remote-linux.sh <ref> -- <run options>` runs it on the Linux test host (`COD4E_LINUX_HOST`) and copies `bundles/` back.

Stage 3 (`client-flythrough`) needs a GPU and a display: it runs the `cod4e` client (`$COD4E_CLIENT`, else next to the harness) on mp_crash once per display mode (native borderless, windowed 1080p and 720p, plus an exclusive run at another native-size refresh when the monitor has one), 12 s each (`COD4E_FLYTHROUGH_SECS`), and records one short video (a few MB), a screenshot and per-frame timings per mode. It also runs mp_crash uncapped at native size (`--present immediate` and `mailbox`) and two more stock maps (mp_bog, mp_crash_snow), so the bundle shows sun shadows, fog and the film/glow post effects on three maps. `frames.csv` carries GPU pass time from timestamp queries where the device has them (`gpu_ms`, a few frames behind the render call, matched by frame number). Without the client, an install or a display it is skipped.

## Headless server

```sh
COD4_PATH=/path/to/install nix develop -c cargo run --release -p server -- +set g_gametype war +exec server.cfg +map mp_crash
```

`cod4e-server` boots like the original's dedicated server: command-line `set`s, `default_mp.cfg`, the dedicated zone set, then `+exec` and `+map`. It runs the stock gametype scripts at 30 Hz (`sv_fps`) on one thread. Console commands include `bots N` (server-side test clients that pick a team and class and play: they roam a navigation mesh generated from the map's collision data, shoot enemies they see, and inject usercmds directly, with no netchan), `status` and `expect <stat> <min>`. Harness stage 2 (`headless-bots`, plus `headless-bots-sd` for Search and Destroy; every server stage fails over 512 MiB peak RSS) plays an 18-bot team deathmatch round on mp_crash to its time limit and the map rotation, and records `ticks.csv` (per-tick total and gsc/bot/client/game columns), RSS, map-load and navigation-generation time and match counters; `headless-bots-32` is the 32-player budget run. Stage `script-pool` plays 32 Search and Destroy rounds and a two-map team deathmatch rotation with bots and fails if the script variable pool (the original's 0xFFFE-value limit) does not return to the same level every round.

### Use triggers

`+activate` works as in the original (`src/activate.rs`): each frame the server picks the player's use trigger (`trigger_use` by the view and range, `trigger_use_touch` by standing in it, a trigger switched off for the player's team or claimed by another player does not count) and puts its cursor hint (`cursorHint`, `cursorHintString`, `cursorHintEntIndex`) in the player state; a fresh press on a hinted trigger sends it `trigger` with the player once `g_useholdspawndelay` and `g_useholdtime` allow, and a held button is not a fresh press until it is let go. The client draws the hint (owner-draw 72, `cg_cursorHints`). Search and Destroy and Sabotage plant and defuse through this: bots walk to a zone, pickup or defuse trigger that is on for their team and hold the button there (a free bomb pickup first; a carrier or a defender sent to a just-planted bomb does not stop for far-off enemies; they stand still, not sprinting, so the server takes the press). Harness stages `headless-sd-objective` and `headless-sab-objective` (8 and 16 bots, the server runs unpaced with `until plants 1 <seconds>`), `net-objective` (two real UDP clients; one plants holding +activate at the zone's hint, the other defuses; the stage places them with `devtele`) and `client-objective` (the real client plants; needs a display).

Dropped weapons and live grenades (`src/items.rs`, `sim::weapon::pickup`): `dropitem` (and the stock `dropWeaponForDeath`) leaves an item entity holding the player's magazine and the reserve their other weapons could not carry; it falls with the `g_drop*Speed*` velocities, at most `g_maxDroppedWeapons` stay (the one farthest from every player is freed), and the dropper cannot take it back for a second. Clients are sent it as an `ITEM` entity and draw the weapon's world model. Walking over one feeds a weapon the player owns (or shares ammunition with) up to its limit and plays `ammoPickup`/`pickup` sounds; +activate on a hinted one takes the weapon with its ammunition (swapping out the primary in hand when both slots are full). A live frag at rest within `player_throwbackInnerRadius` shows the throw-back hint; the grenade key takes it with the fuse left (`player_throwbackOuterRadius`, `bg_maxGrenadeIndicatorSpeed`). A player who dies cooking a grenade drops it with the fuse left, and Martyrdom (`perk_grenadeDeath`) drops another. `ItemWeaponSetAmmo` sets what an item holds. Not built: `dropitem`'s second argument (the weapon tag the item leaves from), the pickup HUD icon (`CG_ItemPickup`), and map `weapon_*` entities settling onto the floor.

### Action slots, hardpoints and votes

`setactionslot(n, "weapon" name | "altmode" | "nightvision" | "")` fills one of the four slots of the player state; `+actionslot N` on the client selects the slot's weapon (pressed again, the one held before), toggles the alternate weapon or the night vision, and the d-pad pieces (owner-draws 165-169) show them. The server now honours the weapon a person asks for (the weapon keys and slots). The killstreak UAV is earned into slot 4 by the stock scripts and called in by selecting it (harness stage `headless-hardpoint`: bots do it and the script's use is counted). The airstrike picks its target on the full-screen map: `beginLocationSelection` puts the selector in the player state, the mouse moves the point (owner-draw 186 draws the selector circle), the attack key confirms and the server answers `confirm_location` with the world point (`setMiniMap` supplies the map's size and north) or `cancel_location` (melee or reload); harness stages `headless-airstrike` (bots) and `client-hardpoint` (the real client: `+actionslot 4`, the d-pad pieces 166/168/169, the map pick).

The helicopter hardpoint runs on the stock scripts: `spawnHelicopter` makes a script vehicle that flies toward the goal `setVehGoalPos` gives it (speed, acceleration, yaw rate, pitch and roll limits, stops and hover as the original's AI move), a turret tracks `setTurretTargetEnt` and notifies `turret_on_target`, `fireWeapon` shoots its 20 mm bullets and homing rockets, and `G_Damage` on it reaches the script as `damage`, so it can be shot down (bots shoot enemy helicopters). `level.heli_paths` come from the map's `heli_start`, `heli_dest` and `heli_loop_start` entities. Clients are told of it as a vehicle entity. `spawnPlane` makes the airstrike's planes. Harness stage `headless-helicopter`: a bot calls it in, it flies, fires and is shot down. Not simulated: the body jolt when hit, the turret's moving barrel bone on the server (aim uses rest-pose tags), map collision for vehicles, hellfire and javelin guidance.

The client draws script vehicles (`VEHICLE` entities, the helicopters): interpolated between snapshots like the other players, the model's rotors turning with the `bh_rotors` animation (the rest of the model stays at its rest pose), the vehicle's sound loops following it and its weapon's fire sound and muzzle flash at the muzzle. Harness stage `client-heli`: a bot calls the helicopter in, the player is held behind and beside it every frame (`devheli view human`) and the picture must differ from the same view with `drawvehicles 0`.

The client draws missiles (`MISSILE` entities: thrown grenades, rockets, C4, claymores) as the weapon's projectile model along the entity's `angles`, with its trail effect pointing along the networked `velocity`, and loops the weapon's `projectileSound` on a missile in flight. An explosion event carries the surface it sat on: the client plays the impact table's blast and sound for that surface and then the weapon's `projExplosionEffect` and `projExplosionSound` (a flashbang or a dud has only its own); a missile that will not go off sends a dud event (`projDudEffect`, `projDudSound`). `devgrenade <human|client> <weapon> [speed] [fuse_ms]` throws one for tests; harness stage `client-missile` asserts the model is drawn and the explosion is received and heard.

`callvote` and `vote` run in the server (`src/vote.rs`, the original's `g_oldVoting`): `map`, `typemap`, `g_gametype`, `map_restart`, `map_rotate`, `kick` and `tempBanUser` (which also refuses the address for `sv_kickBanTime` seconds, 300 by default) pass on a majority of the people playing (bots count as voters, spectators do not; an abstention weighs `g_voteAbstainWeight`, 0.5, when time runs out) and run three seconds later, or fail after 30 s; `g_allowvote` switches them off. Harness stage `net-vote` has two real UDP clients kick one of them and change the gametype and map. `map_restart` loads the level afresh with the latched `g_gametype` and `sv_maxclients` (so a gametype vote works), `fast_restart` restarts in place unless one of them changed, and `map_rotate` skips words it does not know and wraps. `getinfo` carries `pswrd`, `ff`, `kc`, `hw`, `mod`, `pure`, `voice`, `pb`, `minPing` and `maxPing`, `getstatus` the server info and the players, and the configstrings `SERVERINFO`, `SYSTEMINFO` and `CODINFO` are published. `g_log` (`games_mp.log`) records `InitGame`, `ShutdownGame`, chat and the scripts' `logPrint` lines. A client's `userinfo` (name through `ClientCleanName`, `rate`, `snaps`) is read by the server, with `sv_maxRate` pacing; the client sends it on connect and the `name` command sends a new name. `g_inactivity`, the cheat/init/range rules of console variables, `pingPlayer` and the night vision notifies are in too. Voice chat and the talker icons (owner-draws 193-196) are not built: no voice is sent or played, and the pieces draw nothing.

The server console reads stdin, and with `rcon_password` set a UDP `rcon <password> <command>` runs the same commands with their output returned as `print` packets (1294-byte chunks; one request per 500 ms; bad attempts are logged). Operator commands: `status` (num score ping guid name lastmsg address qport rate; ping is `BOT`, `CNCT` or `ZMBI` when there is none to show; guid and rate are placeholders, this server has neither), `kick`/`tempBanUser`/`clientkick`/`tempBanClient` (the first and third by name or number; a brief ban of `sv_kickBanTime` seconds, or none for `onlykick`/`clientkick`), `banUser`/`banClient` (permanent, kept by address in `sv_banFile`, default `ban.txt`), `unbanUser <ip>`, `say`, `tell`, `systeminfo`, `dumpuser`, `toggle`, `reset`, `setfromdvar`, `cvarlist`; `heartbeat` only says there is no master server. Harness stage `net-rcon` drives them from a UDP socket. A client the server drops is told why (`Player kicked`, `Server command overflow`) and the others read `<name> left the game` / `was kicked` / `timed out`; a client that hears nothing for `cl_timeout` seconds (default 40) returns to the menu with `Server connection timed out`, and the `reconnect` console command rejoins the last server.

### Browser clients (WebTransport)

`--webtransport [host:]port` (cvar `net_wt`, empty = off) also serves WebTransport next to UDP: a browser sends and receives the same datagrams as a UDP client (connect packets and netchan), peers named by their QUIC address. A datagram up to the session's maximum datagram size (capped at 1200 bytes, the browsers' limit) is one WebTransport datagram; a longer one, up to 8192 bytes, is one unidirectional stream carrying exactly those bytes, ended by FIN; both forms are accepted in both directions (`net::wt` module docs). Anyone may connect; bans, rate limits and the password apply to the connect packets as for UDP.

Without `--wt-cert cert.pem --wt-key key.pem` (cvars `net_wt_cert`, `net_wt_key`) the server makes an ECDSA P-256 certificate valid 13 days at each start and logs its SHA-256 (base64 and hex). With `--wt-info file.json` (`net_wt_info`) it writes what the page needs for `new WebTransport(url, { serverCertificateHashes: [{ algorithm: "sha-256", value }] })`: `{"url":"https://localhost:4433/","certHashSha256Base64":"..."}` (`localhost` when bound to every address, which includes IPv6; a loaded certificate has no hash field). The page decodes the base64 to the 32-byte `value`.

```sh
COD4_PATH=/path/to/install nix develop -c cargo run --release -p server -- --webtransport 4433 --wt-info wt.json +map mp_crash
```

## Playing

`cod4e` with no options starts in the stock main menu, drawn from the install's own menu assets (`ui_mp`/`common_mp` menus, fonts, localized strings and images; `src/ui`). Mouse and keyboard drive it like the original: Start New Server picks a map and gametype and starts a listen server with bots, Join Game takes a server (its list is the LAN, the internet or the favorites, cut to a game mode; the line above it says how the refresh is going; Server Info shows the selected server's settings and players from a `getstatus` query), Options and Controls edit the dvars and binds (click a key slot, press the new key; Backspace clears it; the choices survive in the config file). The default binds are the install's own `default_mp.cfg` (read from its archives, as the original does), then the profile's `config_mp.cfg`; only keyboard look, the mouse wheel and gamepad binds are added by the client, Esc opens the in-game menu. The 640x480 menu space is anchored to a 16:9 safe area at any window shape. `--ui-tour <dir>` opens the menus one by one with no world and saves a screenshot of each (harness stage `client-ui`); `--ui-script click=Start New Server,menu=createserver,click=Start,ingame,shot=a` drives them like a player.

A map loads in the background: one thread decodes the zone, uploads the world and builds the renderer with all its pipelines (on half the cores) while others decode the client content and boot the listen server, and the window keeps presenting the map's `loadscreen_<map>` picture with a progress bar (Esc cancels). A warm-up frame primes the renderer and the player models, so the first frames in the world do not stall either. Harness stage `client-load` asserts the longest gap between presented frames during the load stays under 100 ms on `mp_crash` and the largest map.

In a match the stock HUD menus are drawn with the client's own owner-draw pieces (`src/ownerdraw.rs`): the magazine graphic and reserve, weapon name, grenade counts, the sprint meter, the low-health overlay with the original's pulse phases (`hud_healthOverlay_*`), the hold-breath, mantle and no-ammo hints, and the corner compass with the level's map image (`setMiniMap` and `northyaw`, `src/compass.rs`): it scrolls with the player and turns with the view, shows teammates and, for a couple of seconds, enemies that fire, marks helicopters (owner-draw 155; the stock menus only place it in `compass_old`, so a menu that uses it is needed to see them) and airstrike planes (156, `PLANE` entities from `spawnplane`) with friendly or enemy icons by their owner's team, sweeps a radar line across the map while `setteamradar` or `hasradar` gives the player radar (`ps.radarEnabled`, `compassRadarUpdateTime`) and shows the enemies the sweep passes for `compassRadarPingFadeTime`, and the full-screen map used while picking an airstrike location. The `hud_fade_*`, `hud_enable`, `compass*` and `cg_draw*` dvars apply. Health reaches the client in the player state, so the bar (`cg_drawHealth`) and overlay follow the server. Not done: use-trigger cursor hints (the server does not yet say what the crosshair is on), the d-pad action slots and the talker icons.

```sh
COD4_PATH=/path/to/install nix develop -c cargo run --release -p client -- --listen --bots 9   # solo: a team deathmatch against bots
COD4_PATH=/path/to/install nix develop -c cargo run --release -p client -- --connect host:28960 # a `cod4e-server` (set net_port; default 28960)
```

The client talks to the server over UDP (`net`: sequenced, fragmented netchan, delta-coded snapshots about 36 per second, up to 3 usercmds per packet with redundancy). `--listen` runs the same server inside the client process. The player's own movement is predicted with the very `sim::pm::run_usercmd` the server runs (other players are collision boxes from the snapshot; server corrections fade over 100 ms); other players are drawn 100 ms behind the server clock between two snapshots, and the server rewinds them to that moment when it judges a shot (`g_lagcomp`, at most 250 ms back). Keys, mouse, gamepad and the config file are the input layer's (`bind w +forward`). In a match the mouse is locked whenever no menu is open (no click needed after a menu closes); Esc with no menu to open releases it (it never quits) and a click takes it again. `COD4E_INPUT_DEBUG=1` prints one `input:` line per second to stderr: events per second from GCMouse and winit, which source feeds the look, the GCMouse devices and whether our handler is on each, window focus, pointer lock, and how many frames of motion the focus/lock gate threw away.

Stage 4 (`client-match`) is the real client with `--listen --autoplay`: a scripted player walks toward and shoots the bots for 90 seconds. It asserts connected and spawned, walked, saw the bots, prediction rarely corrected, the view model drawn, every `script_model` the server published drawn, no magenta in the last frame, no stretched skinned triangles, no script errors, shots fired and their impacts, muzzle flashes and pain reaching the client as events and effects (hit registration is the server tests' job, not this stage's, which runs under host load); it reports bandwidth, snapshot rate, frame times and the server's tick cost. It needs a display and skips without one. `net-loopback` and `net-match` cover the protocol and 4 clients with 12 bots without a display; `net-ui` plays the menus a person would (team, class) against Domination and checks the hud elements, objectives, configstrings, client dvars and print lines the stock scripts send (`net::ui` is the client-side contract); `net-killcam` has a bot kill the client and checks the stock killcam replays the killer's view from the server's state ring and ends.

The client draws what the original's cgame draws over the stock HUD menus (`src/hud`): the script hud elements (text, values, timers, materials, clocks, waypoints with an off-screen pointer, with their alignment, move, fade, scale and glow), the `iprintln` and kill-feed message windows (a message is the original's key-and-arguments string: the first localized key, then each argument fills the next `&&1`, `&&2`; the stock `gamemessages`, `boldgamemessages` and `subtitles` menus place them), team-coloured kill lines with the weapon's kill icon, chat, the centre string, the scoreboard rows under the stock top bar (hold Tab; rows ask the server every 2 s), the killcam (the stock `killcam` menu is shown while the server replays a kill) the name of the player a spectator follows with the key help for following (`cg_descriptiveText`; a spectator who follows nobody flies freely, the server running the movement at speed 400 when the scripts allow `freelook`), teammates' names over their heads with the rank icon (fading with distance and line of sight; `cg_drawFriendlyNames`, `cg_overheadNames*`), the name of the player under the crosshair (`cg_drawCrosshairNames`, `cg_enemyName*`/`cg_friendlyName*` fades) and head icons from the scripts' `headicon`/`headiconteam` (bomb and flag carriers) with the connection-interrupted and killcam "you" markers (`cg_scriptIconSize`, `cg_headIconMinScreenRadius`). Harness stage `client-hud` plays a bot match, holds the scoreboard and waits for a kill, and checks what the HUD drew (`hud_draw` in `ui-script.json`, including the overhead and crosshair names; `--ui-script` also takes `scores=on|off` and waits `killcam|dead|intermission|feed`).

A match started from the menus runs on to its end: the scoreboard stays up until the server rotates the map, and the client then loads the next map in the same process (the server's `map` command carries the level; the connection and the player stay), returning to the team and class menus. Start New Server rotates through the stock maps after the chosen one and passes the `scr_*` dvars the player set (time and score limits) to the server, which takes a standard port (28960-28963) when one is free. Join Game asks the server (`getinfo`) which map it plays before loading anything, so a typed address or a listed server joins the right map; its list shows LAN servers (a broadcast and loopback `getinfo` on the standard ports; Refresh List rescans) and favorites (Create Favorite with an address, kept for the session). Stats (rank, unlocks, class setups: the menus' `stat(n)`) belong to the player profile: the profiles of the install's `players/profiles/<name>/mpdata` are listed in Select Profile next to the user's own (`<config dir>/players/profiles`), `active.txt` names the one used last, and New and Delete work (the install is only read: a changed profile is saved to the user's folder, as a decrypted `mpdata` (the CoD 4 X `ice0` form); the original's encrypted `iwm0` files need the CD key and start with fresh stats). The client loads it at start, uploads it to the server when it joins a level, and takes the server's later `setstat` changes back into it.

Harness stage `client-menu-match` runs the client with no flags and a `--ui-script`: Start New Server with a three-kill score limit, team, class, the end-of-match scoreboard, the rotation into the next map, then team and class again and a second spawn. It needs a display and skips without one. Harness stage `client-custom-class` plays from a custom class with a profile's stats: the P90 in the class spawns, the profile's perk and experience stats survive the join, a class change in the grace period applies and every other player is drawn (the client sends its profile right after connecting and the server holds `begin` until it has it, as the original holds the game state until the stats are in). Harness stage `client-ingame-menu` changes team and class mid-round through the in-game menu with `mouse=` clicks and checks that Escape and every pick return to the game, the team changes and the new class spawns, and that each menu lists the stock items (`see=` and `nosee=`). Harness stage `client-frontend` opens the main menu, Select Profile and Create a Class with the install's own profile, steps the game mode chooser (`mouse=#245`, `cvaris=`) and checks that the install's `players/` folder is unchanged. `--ui-script` also has `mouse=<item>` (a click through the pointer), `key=escape`, `nomenu`, `team=<n>|save|other`, `weapon=<name part>`, `set=<console line>`, `connect=<host[:port]>`, `stat=<index> <value>`, `statis=<index> <value>`, `map=<name>[:secs]` and `maprotate[=secs]` steps.

The graphics options take effect: Apply runs `vid_restart`, which moves the window (`r_mode`, `r_displayRefresh`, `r_fullscreen`), sets the present mode (`r_vsync`; a `--present` choice wins) and the screen shape (`r_aspectRatio`, which sets the projection's aspect), and changes a running match's antialiasing (`r_aaSamples`, 2x or 4x multisampling of the scene pass, as far as the device goes), shadows (`sm_enable`), the sun's specular (`r_specular`), depth of field (`r_dof_enable`) and glow (`r_glow_allowed`). Texture size (`r_picmip` with `r_picmip_manual`) and anisotropic filtering (`r_texFilterAnisoMax`) apply to the next map that loads. The saved choices apply at start unless `--size`, `--refresh` or `--fullscreen` was given. `r_vsync` starts at 1 here, not the stock 0. Harness stage `client-gfx` sets them in the menu, applies them with `vid_restart`, starts a match and turns them back, checking the surface's and renderer's own state each time.

## Browser

The `client` crate also builds for `wasm32-unknown-unknown` (`web/`): one build, WebGPU when the browser has it and WebGL2 otherwise (`--backend` / the page's Graphics choice overrides; the F3 overlay shows the backend, frame times and memory). The page reads your install in the browser and never uploads it: pick the install folder (or drop it); with "keep a copy" on, the files the client reads (about 4 GB) are also saved in the browser's private storage (OPFS) so the next visit needs no pick. The wasm runs on the page's main thread and reads the install synchronously through a reader worker (`web/reader.js`, shared memory), so the page needs cross-origin isolation (COOP and COEP headers; `web/serve.py` sends them).

```sh
nix develop -c web/build.sh                 # wasm-bindgen + wasm-opt into web/pkg
nix develop -c python3 web/serve.py 8080    # then open http://localhost:8080/
```

For automated runs `web/serve.py --install <dir>` also serves the install files under `/install/` (development only, never on a public host) and `?dev-install=/install&autostart` makes the page use them without a picker; `?flythrough` flies the camera, `?report=N` posts the overlay values to the server log after N frames. In the browser the pipelines are built a few milliseconds per frame (WebGL2 links shaders serially, 3232 of them on `mp_crash`) instead of all before the first frame: draws whose pipeline is not ready yet are skipped (the F3 overlay shows pipelines built and draws skipped), and `?args=--fly-at 3` holds the flythrough at a fixed time so pictures compare across builds. Harness stage `web-client` does this with a headless Chromium when one is found (`COD4E_CHROME`) and skips otherwise. Harness stage `web-join` starts a native server in the harness (WebTransport on a free port, nine bots in a team deathmatch on mp_crash, certificate hash from `--wt-info`), loads the page with `?connect=127.0.0.1:<port>&cert=<hash>&args=--autoplay --duration 100000`, and waits for the page's report 15 frames after the server put the player in the world (`?report=N` counts from the spawn when `?connect` is given). It passes when the page's `net phase` overlay field (`connecting`, `connected`, `spawned`) says `spawned`, snapshots arrived, surfaces were drawn, and the server itself lists a person (not a bot) playing; it records connect time, snapshots, page CPU ms, wasm memory and frames. It runs `web/serve.py` with `python3` from the PATH (the devshell's), and skips like `web-client`.

`client-fx` runs `cod4e --fx-selftest` (no display, no GPU, the install needed): on mp_crash an explosion draws sprites and then ends, a bullet into the floor plays its impact effect, a shot plays its muzzle flash and ejects a shell that falls under `phys_gravity` and comes to rest, and the vision and shell shock files the stock scripts name are in the install and change the picture. Effects are drawn from server events: impacts, explosions, flesh, `playfx`, and a weapon-fire event for the flash (at the gun's `tag_flash` and `tag_brass` in first person, where a rifle would be for others). Dead players fall as Verlet ragdolls and the map's clutter props are thrown by shots and blasts and effect models with `USE_MODEL_PHYSICS` (brass, debris) and models the script `physicslaunch`ed are PhysPreset rigid bodies (mass, bounce, friction, the model's physics geometry; each client's own simulation, on the map's collision, not shared); `visionsetnaked`, `visionsetnight` and `shellshock` reach the client as commands and drive the glow, film and saved-screen overlays (a shell shock also ducks the sound by channel, fades in its room reverb, rings its tinnitus with end stings and caps how fast the view may turn); the night vision goggles (`n`) blend to the night set. `--fx-demo <effect>` plays one effect in front of the camera every 1.5 s of a `--listen` run.

`client-viewmodel` runs `cod4e --viewmodel-tour 20` on mp_backlot, mp_crash and mp_strike (a GPU adapter and the install needed, no window): the first-person M16 and hands are drawn headless from the spawn points and from points on the way between them, with and without, and the pixels they change must not be dominated by one colour channel and the spawn views must be neither black nor blown out. It guards the reflection probe of moving models, which follows the original's `R_CalcReflectionProbeIndex` (the nearest probe of the cell holding the model, never the solid-red default probe 0 unless the cell has no other); a nearest-anywhere search once picked the default probe near the map's centre and painted the gun red.

Water materials animate with an ocean simulation (`--fx-selftest` checks that the surface moves and spreads on mp_farm's puddles); projectiles in flight play their weapon's trail effect, and trail elements draw as ribbons through the points the effect passed (the selftest flies a rocket and checks that the strip draws and ends). The portal walk clips at the eye rather than the near plane, so a doorway beside the camera no longer hides the view beyond it (mp_crash's alley). The remaining unknowns are settled as follows: mp_bog's blocky facades are the original's nearest-filter, no-mip sampler state, and `iw3mp.exe` writes `D3DRS_SRGBWRITEENABLE` as 0 with no sRGB sampler read found, so textures stay sampled as plain unorm.

`scripts/map-sweep.sh <cod4e> <install> <out> [seconds]` plays every stock map in war, dm, dom, koth, sab and sd with the windowed client (`--listen --autoplay`, five bots) and prints one table row per run (spawned, bots seen, shots fired by anyone, script errors, missing effect/vision/shock files); a run in which nobody fires is repeated at three times the length and fails if it still stays silent (big maps need a while before bots meet). See `scripts/remote-linux.sh` for running it on a display-equipped host.

Controls in the page: click the game to lock the mouse (Esc gives it back and opens the menu; the page drops the lock on its own when the browser takes it, and the next click locks again), F11 or the `togglefullscreen` command switches fullscreen (the canvas and the field of view follow the new size), and a gamepad works through the browser's Gamepad API (`gilrs`; the same binds as native). F3 toggles the overlay, which also shows the view, the pointer lock and the sound output (`running`, `frames_played`, `underruns`, `buffered`, `peak`, `shared`). Sound starts with the page; until the AudioContext is allowed to run (a click or key) frames_played stands still and "Click to enable sound" shows. The sound tables load on the main thread in the browser (a one-off stall at the map load, which counts as underruns).
